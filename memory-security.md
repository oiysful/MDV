## Lessons Learned
- Always run plain `npm audit` (full tree) for the headline supply-chain claim, not `--omit=dev` — devDependencies include electron itself for an Electron app, which is part of the shipped runtime even though npm classifies it as "dev". `--omit=dev` is fine as a *secondary* signal for "what ships in the app bundle" but must never be the sole basis for a "0 vulnerabilities" claim.
- 2026-08-06: user ran `npm audit fix` themselves. Resolved: electron 42.3.0→42.8.0 (moderate GHSA-r4w5) and both undici advisory instances. NOT resolved at the time: brace-expansion (high, GHSA-rgw5-rvv9-x895) and fast-uri (high, GHSA-7p8r-x3mc-p8w7) — confirmed upstream-blocked, not just conservative-fix-blocked: electron-builder hadn't bumped those nested deps yet. **Both later resolved on their own by 2026-08-10's plain `npm audit fix`** (electron-builder's transitive tree had moved on) — a reminder that "upstream-blocked" findings are worth re-checking on every subsequent audit, not written off permanently.
- 2026-08-10: this repo's `.npmrc` sets `min-release-age=7` — npm silently declines to install a fix if the patched version was published less than 7 days ago, even for a plain (non-`--force`) `npm audit fix`. It prints a `npm warn audit ... left at a vulnerable version because a fix is newer than the release-age cutoff` line rather than failing loudly, so it's easy to miss in scrollback. This is a deliberate supply-chain guard (avoids auto-installing a just-published, less-vetted release) — do not bypass it with `--force` or by lowering `min-release-age` reflexively; just re-run the audit after the cooldown passes.
- 2026-09-15: work here is pushed straight to `main` (no PRs since 2026-07-30), so a red CI audit gate blocks nothing and can go unnoticed. The js-yaml runtime advisory above surfaced only because CI was checked after an unrelated push. After every push, check `gh run list --branch main`. Treat an audit-gate failure as a new advisory to triage (fix if the patched version clears the cooldown, otherwise record it here and in the CI allowlist together), not as noise. Likewise, the 2026-08-10 note to "re-run `npm audit` after ~2026-08-13" for dompurify/mermaid sat unactioned for five weeks, leaving the app's own XSS sanitizer on a version with a known advisory. A recheck date written in prose is not a reminder: redo the audit in the next session that touches dependencies or pushes, whichever comes first.

- 2026-09-16: **a feature-branch push runs no CI at all, so the audit gate is silent until a PR opens.** `ci.yml` triggers only on `pull_request` → main and `push` → main. Plan 17 went back to a feature branch (first PR since 2026-07-30, #7), and pushing that branch started nothing — opening the PR is what ran the gate. So the 2026-09-15 lesson's "after every push, check `gh run list --branch main`" only covers direct-to-main work: on a branch, use `gh pr checks <n>` after opening the PR, and know that a branch worked on for days is running no dependency audit the whole time. Neither mode gates anything by itself — `main` still has no branch protection (the API returns 403: private repo, free plan) — so a red gate blocks no merge in either flow and has to be looked at deliberately.

- 2026-09-17: **the `min-release-age=7` cooldown this file credits to "this repo's own `.npmrc`" is not in this repo.** Verified: there is no `.npmrc` here and `git log -- .npmrc` is empty; the setting lives in `~/.npmrc`, the maintainer's user-level npm config. The 2026-08-10 and 2026-09-15 entries above both state it as a repository control and build policy on it — they are kept as written, because they record what was believed then, but the claim is wrong. Practical impact is small (the cooldown bites at `npm install`/`npm audit fix`, which happens on the maintainer's machine where it *is* set; CI only runs `npm ci` from the lockfile and never consults it), yet a fresh clone, a second contributor, or a CI change would silently have no cooldown while this file says otherwise. Committing a one-line `.npmrc` would make the documentation true and the control portable — prefer that over editing the claim. **The wider lesson: a control asserted in security memory is not a control until it is located in the repo.** Re-verify, do not inherit. — **Resolved the same day**: `.npmrc` is now committed with `min-release-age=7`, and `npm config list` confirms the project file overrides the user one. Its role, the attack it covers, the warn-don't-fail behaviour that makes it easy to miss, and the instruction not to `--force` past it are documented in `CONTRIBUTING.md` / `CONTRIBUTING.ko.md` and in the file's own header. Also verified that it does **not** affect CI: `npm ci --dry-run` installs the locked tree cleanly, because `npm ci` reads `package-lock.json` and never consults the cooldown.

- 2026-09-17: **the 2026-09-15 row's closing claim — "brace-expansion/fast-uri… neither is in the tree now, so the entries are stale but harmless" — is false.** `npm ls` finds both packages in the dependency tree. The CI allowlist was therefore not a leftover; it was a live suppression keeping two real packages out of the audit gate, so a future high or critical in either would have passed silently. Nothing was hidden in practice (full tree at 0 high/critical), and the entries are now removed — verified first by running the gate's own script with an empty allowlist against a fresh `npm audit --json`. **This was caught only because the same session re-checked it; the audit report had already repeated the claim verbatim.** That is the second inherited-claim error in two days, after the `.npmrc` one directly above — both were assertions copied out of this file rather than checked against the repo. When a row here says a package, file or setting is present or absent, **run the command**; a sentence in security memory is a record of what someone believed on that date, not a fact about today's tree.

- 2026-09-17: **the audit gate in `ci.yml` is a `node -e '...'` wrapped in a single-quoted shell string, so a single apostrophe anywhere inside it — including in a JS comment — ends the string and hands the rest to bash.** Adding a comment containing `electron-builder's` broke run 35168504489 with `//: Is a directory` (exit 126). What makes this worth recording is that **`bash -n` passes the broken script**: the fragment after the apostrophe is valid shell (`//` reads as a command name), so it fails at runtime, not at parse time. `node --check` on the extracted JS also passes, because the JS itself is fine — the defect is one layer down, in the quoting. The only check that catches it is **running the step**: extract the `run:` block with js-yaml and execute it (`npm audit --json > audit-full.json || true` is safe locally; delete the file afterwards). Do that for any edit to an embedded script in a workflow, and keep apostrophes out of that block entirely.

- 2026-09-17: **three Electron tests are load-dependent flakes, and that is a security problem, not just an annoyance.** The copy-button hover test, the default-app-guide focus test, and (until `fcd7015`) the ⌘B focus-guard test each pass 3/3 in isolation and fail intermittently only under the full suite, where several Electron instances contend for OS focus. They share one red/green signal with the dependency audit gate, so every unrelated red trains the reader to say "probably flaky" before opening the log — which happened twice in this one session, including once where I wrongly blamed my own change for a failure that was not mine. **A gate is only as good as the willingness to read it.** Worth stabilising for that reason alone; `fcd7015` shows the likely shape of the fix (drain the deferred work the app schedules before the test moves focus).
