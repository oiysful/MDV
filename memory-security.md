## Lessons Learned
- Always run plain `npm audit` (full tree) for the headline supply-chain claim, not `--omit=dev` — devDependencies include electron itself for an Electron app, which is part of the shipped runtime even though npm classifies it as "dev". `--omit=dev` is fine as a *secondary* signal for "what ships in the app bundle" but must never be the sole basis for a "0 vulnerabilities" claim.
- 2026-08-06: user ran `npm audit fix` themselves. Resolved: electron 42.3.0→42.8.0 (moderate GHSA-r4w5) and both undici advisory instances. NOT resolved at the time: brace-expansion (high, GHSA-rgw5-rvv9-x895) and fast-uri (high, GHSA-7p8r-x3mc-p8w7) — confirmed upstream-blocked, not just conservative-fix-blocked: electron-builder hadn't bumped those nested deps yet. **Both later resolved on their own by 2026-08-10's plain `npm audit fix`** (electron-builder's transitive tree had moved on) — a reminder that "upstream-blocked" findings are worth re-checking on every subsequent audit, not written off permanently.
- 2026-08-10: this repo's `.npmrc` sets `min-release-age=7` — npm silently declines to install a fix if the patched version was published less than 7 days ago, even for a plain (non-`--force`) `npm audit fix`. It prints a `npm warn audit ... left at a vulnerable version because a fix is newer than the release-age cutoff` line rather than failing loudly, so it's easy to miss in scrollback. This is a deliberate supply-chain guard (avoids auto-installing a just-published, less-vetted release) — do not bypass it with `--force` or by lowering `min-release-age` reflexively; just re-run the audit after the cooldown passes.
