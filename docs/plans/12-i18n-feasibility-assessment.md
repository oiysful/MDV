# 12. 전체 UI i18n(다국어) 적용 타당성 검토

## 상태
**조사 완료. 착수 여부는 사용자 결정 대기.** (이 문서는 실행 계획이 아니라 규모/위험도 산정 보고서 — "진행한다면 이렇게" 수준의 설계만 포함)

## 배경
현재 MDV는 문서(README/CONTRIBUTING/RELEASING)에 대해서만 `.ko.md` 병렬 파일 + 스위처 링크 방식의 문서 레벨 다국어를 갖추고 있다([Bilingual docs] 메모리 참고). 앱 UI 자체(메뉴, 버튼, 툴팁, 토스트, 다이얼로그)는 전량 한국어 하드코딩이며 다국어 전환 기능이 없다. 이번 조사는 앱 UI에 실제 i18n(런타임 언어 전환 또는 최소한 영어 빌드 분리)을 적용할 경우의 규모·위험·권장 착수 여부를 점검한 것이다.

## 조사 결과

### 1. 기존 i18n 인프라 — 없음
`package.json`에 `i18next` 등 i18n 라이브러리 의존성 없음. 문자열은 전부 소스 코드에 리터럴로 박혀 있고, 중앙 문자열 테이블/키 체계가 전혀 없다.

### 2. 한국어 문자열 규모 (파일별, 주석 제외 실사용 텍스트만)

```
78 줄   src/renderer/index.html      (정적 마크업: title/aria-label/버튼 텍스트/온보딩 가이드)
32 줄   src/main.js                  (Electron 네이티브 메뉴 label, 다이얼로그 버튼/메시지, IPC 에러 문자열)
12 줄   src/renderer/app-runtime.js  (빈 상태 안내, alert()/showToast() 메시지)
12 줄   src/renderer/workspace.js    (탭 컨텍스트 메뉴, 닫기 확인 다이얼로그, 파일 변경 안내)
11 줄   src/renderer/app-shell.js    (링크 열기 실패 alert, 폴더 컨텍스트 메뉴)
 6 줄   src/renderer/document-flow.js(파일 변경/저장 실패 안내)
 6 줄   src/renderer/markdown.js     (프론트매터 카드, 코드 복사 버튼, 통계 라벨)
 5 줄   src/renderer/explorer.js     (탐색기 빈 상태/로딩 안내)
 4 줄   src/renderer/editor.js       (분할뷰/줄바꿈 토글 title)
 2 줄   src/renderer/search.js       ("없음" 카운트 표시)
 1 줄   각각 app.js / onboarding.js / theme.js
------
171 줄  실사용 텍스트 (주석 24줄은 별도, 번역 불필요)
```
`index.html`의 `title`/`aria-label`이 같은 문자열을 속성 두 곳에 중복 기재하는 경우가 많아, 고유 문자열 수는 171보다 다소 적지만(대략 120~140개 추정) 여전히 상당한 규모.

### 3. 유형별 특성 — 난이도가 균일하지 않음

- **정적 라벨류** (버튼/툴팁/온보딩 가이드): 단순 문자열 치환으로 끝남. 난이도 낮음.
- **템플릿 리터럴 동적 메시지** (`` `"${tab.filename}"이(가) 외부에서 변경되었습니다...` `` 등, workspace.js:550 / document-flow.js): 한국어 조사(이/가, 을/를)가 변수 뒤에 붙는 구조라 단순 `t('key', {name})` 치환만으로는 안 되고, 언어별 어순/조사 규칙을 감안한 메시지 포맷 재설계가 필요. 영어는 조사 문제가 없지만 이 구조 자체를 문자열 키 시스템으로 옮기는 리팩터링이 필요.
- **Electron 네이티브 메뉴** (`main.js:691-836` `buildMenu()`): 렌더러가 아니라 **메인 프로세스**에서 한 번(`app.whenReady()` 시점, `main.js:217`)만 빌드된다. 현재 아키텍처엔 언어 변경 시 메뉴를 다시 그릴 트리거가 없음 — 런타임 언어 전환을 지원하려면 (a) 언어 설정을 메인 프로세스도 알 수 있게 IPC/영속 저장소 공유, (b) `buildMenu()`를 언어 변경 시 재호출하는 경로 신설이 별도로 필요하다. 렌더러 쪽 문자열 교체보다 구조적으로 손이 더 간다.
- **네이티브 `dialog.showMessageBoxSync`/`alert()`/`confirm()`** (main.js:119-125, workspace.js 다수, app-shell.js:158): OS 네이티브 다이얼로그라 커스텀 UI 다국어 컴포넌트를 못 쓰고, 버튼 라벨까지 포함해 문자열 테이블에서 끌어와야 함.

### 4. 테스트 커플링 — 가장 큰 리스크 요인
현재 테스트 스위트가 **번역 대상 한국어 문자열을 직접 assert**하는 곳이 광범위하다 (예: 버튼 title, 토스트 메시지, 다이얼로그 텍스트를 정규식/문자열 비교로 검증):

```
23줄   tests/electron/boot-and-render.test.js
13줄   tests/electron/menu-and-guides.test.js
 9줄   tests/unit/markdown.test.js
 9줄   tests/unit/csp.test.js
 9줄   tests/electron/explorer-and-shell.test.js
 8줄   tests/unit/app-runtime.test.js
 7줄   tests/electron/links-and-toc.test.js
 6줄   tests/unit/explorer.test.js
 4줄   tests/unit/editor.test.js
 3줄   tests/electron/keyboard-and-a11y.test.js
 그 외 8개 파일에 1~2줄씩
```
문자열을 키 기반으로 바꾸면 이 테스트들이 전부 깨진다. 테스트를 "한국어 문자열이 보이는지"가 아니라 "특정 data-command/클래스/구조가 존재하는지"로 다시 쓰거나, 최소한 기본 언어(한국어) 문자열表만 유지한 채 검증하도록 리팩터링해야 함 — 기능 코드 변경량보다 테스트 수정량이 더 클 수 있는 전형적인 패턴.

### 5. 참고 가능한 기존 패턴
`src/renderer/theme.js`의 `createThemeController`가 좋은 선례다: `storage.getItem('theme')`로 `localStorage`에서 설정을 읽고, `data-theme` 속성으로 전역 적용하며, `storage`를 생성자 인자로 주입해 테스트에서 목(mock) 가능하게 되어 있다(app.js:47,60,132). 언어 설정도 `localStorage`(`lang`) + `data-lang` 속성 + 동일한 주입 패턴으로 구조를 맞추면 렌더러 쪽 아키텍처는 일관되게 갈 수 있다. 다만 이 패턴은 **렌더러 프로세스 안에서만** 유효하고, 위 3번에서 언급한 메인 프로세스 메뉴는 별도 배선이 필요하다.

## 위험도 평가

| 항목 | 평가 |
|---|---|
| 아키텍처 위험 | 중간 — theme.js 패턴을 재사용할 수 있어 렌더러 쪽 설계 자체는 어렵지 않음. 메인 프로세스(네이티브 메뉴) 쪽은 새 IPC 배선이 필요해 별도 설계 필요. |
| 회귀 위험 | **높음** — 테스트 21개 파일·90줄 이상이 리터럴 한국어 문자열에 결합돼 있어, 문자열을 키로 바꾸는 순간 광범위한 테스트 실패가 예상됨. 전수 재검토 없이는 "테스트 통과 = 정상 동작"이 깨질 수 있음. |
| 메시지 품질 위험 | 중간 — 조사(을/를, 이/가)가 붙는 동적 메시지(파일명 삽입 등)는 기계적 치환이 아니라 문구 재작성이 필요해, 번역 품질/자연스러움 검수가 별도로 필요. |
| 범위 누락 위험 | 낮음~중간 — 정적 문자열은 grep으로 소진 가능하나, 동적으로 조립되는 문자열(예: 에러 메시지에 `${res.error}` 같은 IPC 응답 원문이 그대로 섞이는 경우, main.js:397-443)은 번역 대상 여부를 개별 판단해야 함.
| 유지보수 부담 | 신규 문자열 추가 시 항상 2개 언어(또는 그 이상) 동기화가 강제됨 — 지금처럼 "그냥 한 줄 추가"가 안 되고 프로세스가 하나 더 생김. |

## 작업 규모 산정

전면 i18n(런타임 언어 전환, 키 기반 문자열 테이블, 렌더러+메인 프로세스 모두 커버)을 기준으로 단계별로 나누면:

1. **문자열 테이블 설계 + 추출 인프라** (locale JSON 스키마, 렌더러 `t()` 헬퍼, 메인 프로세스용 별도 로더, `theme.js` 패턴을 본뜬 `createI18nController`) — 소규모 신규 모듈이지만 렌더러/메인 두 프로세스에 각각 필요.
2. **~140개 고유 문자열 추출·치환** (index.html 정적 마크업이 최대 비중, 그다음 main.js 메뉴/다이얼로그) — 기계적이지만 양이 많고, 동적 조사(을/를) 문구는 문구 재작성 필요.
3. **메인 프로세스 메뉴 재빌드 배선** (언어 변경 시 `buildMenu()` 재호출 경로, 렌더러→메인 IPC) — 지금 없는 새 흐름.
4. **영어 번역 자체** — 기계 번역 초안 후 검수, 또는 사용자 직접 검수 필요(자연스러움은 코드 조사로 담보 못 함).
5. **테스트 스위트 재정비** — 21개 파일의 한국어 문자열 assertion을 구조적 검증(class/data-command/aria 존재 여부)으로 바꾸거나, 언어 고정(기본값 한국어) 전제로 재작성. **이 작업이 1~4를 합친 것과 비슷하거나 더 큰 규모가 될 가능성이 높음.**
6. **회귀 확인** — 유닛/컨트롤러/Electron 스모크 전체 스위트 재통과 + 실제 앱을 두 언어로 띄워 시각 확인(라이트/다크 × 한국어/영어 = 4가지 조합 스크린샷 점검).

정량적 "N일/N시간" 추정은 이 조사만으로 신뢰성 있게 내기 어렵지만, **정성적으로는 "부분 기능 추가"가 아니라 "코드베이스 전반을 가로지르는 리팩터링" 규모**다 — 지금까지의 단일 기능 단위 계획 문서(문서 01~11)들과 비교하면 자릿수가 다르고, 특히 5번(테스트 재정비)이 병목이 될 가능성이 크다.

## 제안 방안 (착수할 경우)

전면 적용보다 **단계적 축소 착수**를 권장:

1. **1단계 — 렌더러만, 문자열 테이블화 없이 시작**: `theme.js` 패턴을 본떠 `data-lang` 컨트롤러만 먼저 만들고, 신규/수정 코드부터 `t()` 헬퍼를 쓰도록 관례화. 기존 문자열은 한 번에 다 바꾸지 않고 파일 단위로 점진 이관(예: 이번에 만든 alert 기능처럼 새 UI부터 적용).
2. **2단계 — 메인 프로세스 메뉴는 별도 트랙**: 렌더러 이관이 안정화된 뒤에 IPC 배선 + `buildMenu()` 재호출 경로를 붙인다. 지금 구조상 가장 손이 많이 가는 부분이라 먼저 시작하면 병목이 된다.
3. **테스트는 이관과 동시에**: 문자열을 옮기는 PR마다 관련 테스트를 구조적 검증으로 같이 고쳐서, "한꺼번에 90줄 테스트 재작성" 상황을 피한다.
4. 필요하다면 "완전한 런타임 전환" 대신 **영어 빌드를 별도 배포 채널로 분리**(문서의 `.ko.md` 패턴과 유사하게 앱 자체를 언어별 빌드로)하는 대안도 있음 — 런타임 토글보다 구현 범위가 작지만 사용자가 언어를 앱 안에서 못 바꾼다는 트레이드오프가 있다. 이 갈림길은 사용자 결정이 필요.

## 권장 결론
지금 이 시점에 전면 i18n을 한 번에 착수하는 것은 **리스크(테스트 커플링) 대비 즉시 이득이 불분명**하다고 판단된다. 실제 수요(영어 사용자가 얼마나 있는지, 런타임 전환이 꼭 필요한지 vs 별도 언어 빌드로 충분한지)를 먼저 확인한 뒤, 착수한다면 위 "제안 방안"의 1단계(렌더러 점진 이관)부터 작게 시작하는 것을 권장한다.

## 변경 파일 (착수 시 예상 범위 — 실제 작업 시작 전 재확인 필요)
- `src/renderer/index.html`, 모든 `src/renderer/*.js` (문자열 소스)
- `src/main.js` (네이티브 메뉴/다이얼로그, 메인 프로세스 언어 배선)
- 신규: `src/renderer/i18n.js`(가칭, theme.js 패턴), 언어별 문자열 테이블 파일
- `tests/unit/*.test.js`, `tests/controller/*.test.js`, `tests/electron/*.test.js` 전반 (21개 파일)

## 리스크 / 미결정 사항
- 런타임 언어 전환 vs 언어별 별도 빌드 — 요구사항 확정 필요(위 "제안 방안" 4번).
- 동적 메시지의 조사(을/를, 이/가) 문제를 어떤 방식으로 해결할지(라이브러리 사용 vs 문구 재설계로 회피) 결정 필요.
- 번역 품질 검수를 누가/어떻게 할지(기계 번역 초안 + 사용자 검수 vs 별도 번역 리소스) 미정.
