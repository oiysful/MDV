# 20. 복사 테스트 플레이크 + 플레이크 목록 문서 정합

## 상태
**계획 (미착수)** — 2026-09-18 작성.

두 가지를 한 계획서로 묶는다. 서로 다른 일이지만 **같은 뿌리에서 나왔다**: 플레이크 목록이
두 문서로 갈라져 각자 다른 세상을 기록하고 있었고, 그래서 네 번째 플레이크가 세 번의 수정
(계획 18의 2건, 계획 19의 1건) 내내 아무도 모르는 채로 남아 있었다.

| 항목 | 내용 |
|------|------|
| A | `boot-and-render.test.js`의 복사 테스트 플레이크 진단 및 수정 |
| B | `AGENTS.md` / `security-report.md` / `memory-security.md`의 플레이크 목록 정합 |

A를 먼저 하고 그 결과까지 B에 반영한다. 순서를 뒤집으면 B를 두 번 쓰게 된다.

## Context — 어떻게 드러났나

계획 18 작업 중 `boot-and-render.test.js`의
**`openFile loads markdown, updates title, and renders code highlighting`**(250행)이
병렬 실행에서 한 번 **15.8초 타임아웃**으로 죽었다. 이후 7회(2파일 조합 6회 + 전체 1회)에서
재현되지 않았고 출력을 잡지 못해, 계획 18의 커밋 본문에 **미해결로 기록**했다.

그 뒤 `security-report.md`와 `memory-security.md`(둘 다 2026-09-17)가 **"Electron 테스트 3건이
부하 의존 플레이크"** 라고 적어 둔 것을 확인했고, 그 3건 중 하나인 "copy-button hover test"가
바로 이 테스트다. 즉 **미해결이 아니라 이미 문서화돼 있던 네 번째 플레이크**였다. 두 문서가
서로를 참조한 적이 없어서 계획 18/19 내내 시야에 들어오지 않았을 뿐이다.

증상이 제 코드가 아니라는 근거: 이 테스트의 기본 타임아웃(15초) 대기는 5개
(`#empty`, `document.title === 'basic'`, `::after` opacity===1, `.copied`, `::after` opacity===0)이고,
계획 18이 넣은 `waitForToast`는 상한이 5초다. **15.8초는 저 5개 중 하나다.**

## 진단 A — 가장 유력한 가설: 클립보드는 문서 포커스를 요구한다

> **주의: 아직 재현으로 확정하지 않았다.** 아래는 코드로 특정한 가설이고, 착수 시 첫 일은
> 이 가설의 결정적 재현이다. 계획 18에서 배운 대로, 코드상 그럴듯한 원인이 곧 실제 원인은 아니다.

`app-runtime.js#copyCode`:

```js
async function copyCode(button) {
  const code = button.closest('.code-wrapper').querySelector('code')
  try {
    await navigator.clipboard.writeText(code?.innerText || '')
  } catch (err) {
    showToast('코드 복사 실패')
    return                      // ← .copied를 붙이지 않고 빠져나간다
  }
  button.innerHTML = CHECK_ICON
  button.classList.add('copied')
  showToast('코드 복사됨')
  ...
}
```

Chromium의 async Clipboard API는 **문서가 포커스를 갖고 있어야** 동작하고, 그렇지 않으면
`NotAllowedError: Document is not focused`로 거부한다. 거부되면 catch가 **early return** 하므로
`.copied`가 영영 붙지 않고, 바로 다음 줄의

```js
await page.waitForFunction(() => document.querySelector('#content .copy-btn')?.classList.contains('copied'))
```

가 15초를 통째로 소진한다. **관측된 15.8초와 모양이 맞는다.**

병렬 실행에서 여러 Electron 인스턴스가 차례로 뜨며 OS 포커스를 가져가므로 부하가 클수록
잦아진다 — 보안 문서가 "contend for OS focus"라고 적은 것과 같은 현상이고, 이 가설은 거기에
**정확한 기전**을 붙인다.

`copyAll`(`#btn-copy-all`)도 같은 구조다. 다만 그쪽은 계획 18이 `waitForToast`로 바꿔 두어서,
실패하면 `no recorded toast matched /^복사됨$/, got ["복사 실패"]`로 **원인이 메시지에 드러난다.**
`.copied` 대기 쪽만 여전히 맨 타임아웃이 난다.

### 앱 결함이 아니라 테스트 결함인 이유

포커스 없는 창에서 클립보드 쓰기가 거부되는 것은 브라우저의 의도된 동작이고, 실제 사용자는
버튼을 누르는 순간 반드시 창이 포커스를 갖고 있다. 앞의 세 건과 같다 — **앱은 옳고 테스트가
현실에 없는 조건을 만든다.**

## 검증 절차 A (착수 시 가장 먼저)

가설을 **결정적으로** 재현한다. 계획 18/19에서 쓴 방법 그대로, 조건을 인위적으로 강제한다.

1. `navigator.clipboard.writeText`를 `NotAllowedError`로 거부하도록 스텁한 뒤 현재 테스트를 돌린다.
   → `.copied` 대기에서 15초 타임아웃이 나야 한다. 나면 기전 확정.
2. 가능하면 진짜 조건으로도 한 번: 클릭 직전에 창의 포커스를 떼고(다른 창을 띄우거나
   `BrowserWindow#blur()`) 같은 실패가 나는지 본다. 1번이 기전을, 2번이 **현실성**을 준다.

1번이 실패하면(= 타임아웃이 안 나면) 가설이 틀린 것이므로 나머지 네 개 대기로 후보를 옮긴다.
특히 hover 기반 `::after` opacity 대기 두 개가 다음 후보다.

## 설계 A (가설이 맞을 경우)

> 확정 전이므로 방향만 적는다. 재현 결과에 따라 바뀔 수 있다.

**창을 넓히는 쪽은 하지 않는다.** "클릭 전에 창을 포커스한다"는 한 줄은 그럴듯하지만,
포커스는 다음 순간 다른 인스턴스가 다시 가져갈 수 있다 — 계획 19의 400ms와 같은 종류의
**창**이지 장벽이 아니다. 이 저장소가 이미 세 번 거부한 모양이다.

의존 자체를 없애는 쪽이 맞다. 관찰: **이 테스트는 클립보드 내용을 검증하지 않는다.**
검증 대상은 전부 UI 반응이다 — 아이콘이 체크로 바뀌는 것, `.copied` 클래스, 토스트, 툴팁이
숨는 것. 따라서 `navigator.clipboard.writeText`를 해소되도록 스텁하면 **모든 단언은 그대로
의미를 유지한 채** OS 포커스 의존만 사라진다.

**다만 대가가 있다:** 실제 클립보드 경로의 커버리지가 사라진다. 착수 시 먼저 확인할 것 —
저장소의 다른 테스트가 클립보드를 되읽어 검증하는 곳이 있는가? 없다면 둘 중 하나를 고른다.

1. UI 반응 테스트는 스텁으로 결정화하고, 실제 쓰기는 별도의 좁은 테스트 하나로 남긴다.
   그 테스트는 포커스를 명시적으로 확보하고, 실패 시 `복사 실패` 토스트를 근거로 **왜**
   실패했는지 드러나게 한다.
2. 커버리지 상실을 감수하고 스텁만 한다.

1번을 권하지만, 실제 쓰기 테스트가 같은 이유로 불안정해질 수 있으므로 착수 시 판단한다.

## 진단 B — 플레이크 목록이 두 문서로 갈라져 있다

같은 주제를 세 문서가 각자 적고 있고, 서로를 참조하지 않는다.

| 테스트 | 실제 상태 | `AGENTS.md` | 보안 문서 2종 |
|---|---|---|---|
| `large-directory-watch` path-count guard | 수정됨 (계획 18) | 있음 | **없음** |
| `split-view-async` fresh preview | 수정됨 (계획 18) | 있음 | **없음** |
| default-app-guide focus | 수정됨 (계획 19) | 있음 | **"열림"으로 남아 있음 — 낡음** |
| copy-button hover (= 이 계획서 A) | **열림** | **없음** | 있음 |
| ⌘B focus-guard | 수정됨 (`fcd7015`) | 없음 | 있음 (이미 "until `fcd7015`"로 표기) |

즉 **두 목록의 교집합이 한 건뿐**이고, 그 한 건조차 한쪽만 최신이다.

이건 `memory-security.md`가 스스로 적어 둔 실패 양식과 같은 것이다 — 그 파일의 2026-09-17
항목은 "이 파일의 한 줄은 그날 누군가가 믿었던 기록이지 오늘의 사실이 아니다"라고 경고하면서
**상속된 주장을 확인 없이 되풀이한 사고 두 건**을 기록해 두었다. 플레이크 목록이 정확히
그 상속된 주장이 됐다.

보안 문서가 이걸 다루는 **이유 자체는 유효하고 유지해야 한다**: 플레이크는 의존성 audit
게이트와 같은 빨강/초록 신호를 공유하므로, 무관한 빨강이 반복되면 독자가 로그를 열기 전에
"아마 플레이크겠지"라고 말하게 훈련된다. `security-report.md`가 "게이트는 그걸 읽을 의지만큼만
쓸모 있다"고 적은 그대로다. 없앨 내용이 아니라 **한 곳으로 모으고 나머지는 참조**할 내용이다.

## 설계 B

1. **정본을 `AGENTS.md`로 정한다.** 운영 지침이 사는 곳이고, 이미 계획 18/19의 기록이 거기 있다.
   copy-button hover 건을 추가하고(= A 수정 후에는 그 결과로), `fcd7015`의 ⌘B 건도 역사로 편입해
   **다섯 건이 한 표에서 보이게** 한다.
2. **`security-report.md`는 현재 상태 문서이므로 제자리 갱신.** 3건 나열을 걷어내고,
   게이트 신뢰 문제라는 논지 + `AGENTS.md`/계획서 참조로 바꾼다. "Next Steps"의 안정화 항목도
   남은 실제 건수에 맞춘다.
3. **`memory-security.md`는 날짜 기록이므로 덮어쓰지 않고 추가한다.** PR #13에서 같은 파일에
   이미 확립한 방식이다 — "그날의 판단"은 보존 가치가 있으므로 정정을 **append** 한다.
   추가할 내용: 3건 중 2건은 그 뒤 수정됐고, 목록이 `AGENTS.md`와 갈라져 있었으며, 그 갈라짐
   자체가 이 파일이 경고한 상속된 주장의 또 다른 사례라는 것.
4. **재발 방지 규칙 한 줄.** 플레이크 목록은 `AGENTS.md`에만 두고, 다른 문서는 참조만 한다.
   두 곳에 같은 목록을 두면 반드시 갈라진다 — 이번이 그 증거다.

## 검증 계획

- **A**: 위 "검증 절차 A". 수정 후에는 앞의 세 건과 같은 기준 — **터뜨리려고 만든 조건에서도
  통과**하는지. 그 뒤 전체 스위트 `--test-concurrency=2` 반복 + CI 같은 커밋 3회 연속 그린.
- **B**: 문서이므로 테스트가 없다. 대신 **표의 다섯 행을 한 줄씩 실물과 대조**한다 —
  각 테스트가 지금 존재하는지, 수정 커밋이 실재하는지, 줄 번호와 인용이 맞는지.
  이 계획서가 고치려는 결함이 바로 "확인 없이 상속된 주장"이므로, 여기서 그걸 반복하면 안 된다.

## 하지 않을 것

- **`--test-concurrency` 재조정.** 네 번째 오진이 된다.
- **고정 지연이나 포커스 한 줄로 창 넓히기.** 계획 19가 같은 이유로 거부했다.
- **프로덕션 코드 수정.** 포커스 없는 창에서 클립보드 쓰기가 거부되는 것은 올바른 동작이다.
  (단 A의 재현이 이 가설을 뒤집으면 이 항목도 다시 본다 — 계획 18에서 진단이 바뀌었듯이.)
- **보안 문서에서 플레이크 논의를 삭제.** 게이트 신뢰 논지는 유효하다. 옮기는 것이지 지우는 게 아니다.
