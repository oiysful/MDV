# 20. 복사 테스트 플레이크 + 플레이크 목록 문서 정합

## 상태
**수정 완료** — 2026-09-18 계획, 2026-09-21 진단·수정.

두 가지를 한 계획서로 묶었다. 서로 다른 일이지만 **같은 뿌리에서 나왔다**: 플레이크 목록이
두 문서로 갈라져 각자 다른 세상을 기록하고 있었고, 그래서 네 번째 플레이크가 세 번의 수정
(계획 18의 2건, 계획 19의 1건) 내내 아무도 모르는 채로 남아 있었다.

| 항목 | 내용 | 결과 |
|------|------|------|
| A | `boot-and-render.test.js`의 복사 테스트 플레이크 진단 및 수정 | 수정 완료 — **계획서의 주 가설은 실측으로 기각됐고 원인은 다른 것이었다** |
| B | `AGENTS.md` / `security-report.md` / `memory-security.md`의 플레이크 목록 정합 | 완료 — 정본은 `AGENTS.md` 하나 |

A를 먼저 하고 그 결과까지 B에 반영했다.

## Context — 어떻게 드러났나

계획 18 작업 중 `boot-and-render.test.js`의
**`openFile loads markdown, updates title, and renders code highlighting`**(250행)이
병렬 실행에서 한 번 **15.8초 타임아웃**으로 죽었다. 이후 7회(2파일 조합 6회 + 전체 1회)에서
재현되지 않았고 출력을 잡지 못해, 계획 18의 커밋 본문에 **미해결로 기록**했다.

그 뒤 `security-report.md`와 `memory-security.md`(둘 다 2026-09-17)가 **"Electron 테스트 3건이
부하 의존 플레이크"** 라고 적어 둔 것을 확인했고, 그 3건 중 하나인 "copy-button hover test"가
바로 이 테스트다. 즉 **미해결이 아니라 이미 문서화돼 있던 네 번째 플레이크**였다. 두 문서가
서로를 참조한 적이 없어서 계획 18/19 내내 시야에 들어오지 않았을 뿐이다.

## 진단 A — 가설은 틀렸다

계획서가 세운 가설은 **"클립보드는 문서 포커스를 요구한다"** 였다. Chromium의 async Clipboard
API는 문서가 포커스를 갖고 있어야 하고, 아니면 `NotAllowedError: Document is not focused`로
거부한다. 거부되면 `copyCode`의 catch가 early return 하므로 `.copied`가 영영 붙지 않고, 바로
다음 줄의 `.copied` 대기가 15초를 통째로 소진한다 — 관측된 15.8초와 모양이 맞았다.

계획서는 이 가설을 **"아직 재현으로 확정하지 않았다"** 고 명시하고, 착수 시 첫 일을 결정적
재현으로 못박아 두었다. 그게 이 문서를 구했다.

### 프로브 1 — 기각

`launchApp()` 직후 창의 포커스를 세 방법으로 떼고 측정했다.

| 조건 | `document.hasFocus()` | `navigator.clipboard.writeText` |
|---|---|---|
| 기본 | `true` | `ok` |
| `BrowserWindow#blur()` 후 | `true` | `ok` |
| `minimize()` 후 | `true` | `ok` |
| `hide()` 후 | `true` | `ok` |

**Playwright 하의 Electron에서는 문서가 항상 포커스된 것으로 취급된다.** 가설이 요구하는
거부는 이 하네스에서 일어날 수 없다. 기전도 현실성도 없다.

보안 문서 2종이 2026-09-17부터 적어 온 **"여러 Electron 인스턴스가 OS 포커스를 두고 경합한다"**
는 설명도 같이 무너진다. 그 문장은 확인된 적 없이 상속돼 왔다.

### 프로브 2 — 실제 원인: `.copied`는 상태가 아니라 창이다

`copyCode`는 1.5초 뒤 `.copied`를 걷어낸다(`app-runtime.js`). 클릭 후 대기 시작을 1700ms
늦추고 측정했다.

```
late .copied wait outcome = "TimeoutError"      ← 타임아웃 예산 전부 소진
class transitions [ms, hasCopied] = [[22,true],[1524,false]]
toasts recorded = ["코드 복사됨"]                ← 클립보드는 성공했다
::after opacity (창 종료 후) = "1"
```

세 가지가 한꺼번에 드러난다.

1. `.copied`는 **22ms에 붙고 1524ms에 사라지는 1.5초짜리 창**이다. 늦게 시작한 대기는 그 창을
   영영 보지 못하고 15초를 소진한다.
2. **클립보드는 성공했다.** 토스트 기록이 `코드 복사됨`이다. 실패한 것은 복사가 아니라 관측이다.
3. 창이 닫히면 `::after` opacity가 **1로 되돌아간다**. `.copy-btn.copied::after { opacity: 0 }`
   이므로 다섯 번째 대기(opacity `0`)도 같은 창에 묶여 있다.

즉 **하나의 만료되는 조건 위에 단언 세 개가 사슬로 얹혀 있었다** — `.copied` 클래스, 체크
아이콘(`innerHTML`), 숨은 툴팁. 이것은 계획 18이 `#toast`의 1.6초 `show` 창에서 이미 한 번
고친 것과 **정확히 같은 결함 계열**이다. 저장소가 같은 모양에 두 번 당했다.

### 앱 결함이 아니라 테스트 결함인 이유

바뀌지 않는다. 다만 이유가 다르다. 포커스 없는 창에서 클립보드가 거부되는 것이 옳은 동작이라서가
아니라(그런 일은 일어나지 않았다), **일시적인 시각 상태를 1.5초 뒤 되돌리는 것이 옳은 UI**이기
때문이다. 테스트가 그 일시성을 상태처럼 다룬 것이 결함이다.

## 설계 A — 창을 넓히지 않고, 테스트가 창을 연다

창을 넓히는 쪽은 하지 않았다. 계획 19가 같은 이유로 거부한 선택이다 — 고정 지연은 항상 그것을
앞지르는 부하가 있다.

클립보드를 스텁하는 계획서의 원안도 폐기했다. 프로브 2가 클립보드는 성공한다는 것을 보였으므로,
스텁은 **원인이 아닌 것을 고치면서 실제 클립보드 경로의 커버리지만 잃는** 거래가 된다. (`copyCode`의
성공/거부 두 분기는 `tests/unit/app-runtime.test.js`가 이미 스텁으로 덮고 있어, Electron 테스트가
유일하게 쥔 것은 진짜 Chromium 쓰기뿐이다. 그걸 버릴 이유가 없다.)

채택한 것은 **계획 19의 게이트**다. 복원 타이머를 테스트가 붙잡고, 풀 시점을 테스트가 정한다.

- `armCopyResetGate(page)` — 페이지 쪽 `setTimeout`을 감싸 1500ms 타이머를 보관한다.
- 창이 무한히 열려 있으므로 `.copied`·아이콘·툴팁 단언은 **의미를 그대로 유지한 채** 경쟁에서 벗어난다.
- `releaseCopyResetGate(page)` — 보관한 콜백을 실행해 복원을 일으킨다. 그 덕에 **복원 자체를 처음으로
  단언**하게 됐다(아이콘이 `icon-copy`로 되돌아오고 `.copied`가 떨어지는 것). 커버리지가 줄지 않고 늘었다.
- `waitForTooltipOpacity(page, expected)` — 게이트가 덮지 못하는 유일한 대기(hover 시 opacity `1`)를
  `waitForToast`와 같은 방식으로 계측했다. 타임아웃 시 실제 관측된 opacity를 보고하므로, 다섯 개 중
  이것이 범인이었던 경우 다음번엔 스스로 밝힌다.

### 게이트가 엉뚱한 타이머를 잡는 경우

`delay === 1500` 매칭은 `app-runtime.js`와의 구조적 결합이다. 상수가 드리프트하면 게이트가 조용히
작동을 멈추고 테스트가 원래의 창 경쟁으로 되돌아간다 — 신호 없이.

**개수 단언만으로는 이걸 못 잡는다는 것을 실측했다.** `COPY_RESET_DELAY_MS`를 1600으로 바꾼 사본은
`heldCopyResets.length === 1` 단언을 **통과했다**. 게이트가 `#toast`의 1.6초 타이머를 대신 잡았고,
진짜 복원 타이머는 예정대로 돌았기 때문이다. 그래서 시간 기반 단언을 추가했다 — 복원 지연을 넘겨
기다린 뒤에도 창이 열려 있어야 한다. "창이 닫히지 않았다"는 명제는 경과 시간만이 뒷받침할 수 있다.

확인했다.

## 진단 B — 플레이크 목록이 두 문서로 갈라져 있었다

착수 시 다섯 행을 전부 실물 대조했다. 이 계획서가 고치려는 결함이 "확인 없이 상속된 주장"이므로
여기서 그걸 반복할 수는 없었다 — 그리고 실제로 **계획서 자신의 표가 이미 낡아 있었다.**

| 테스트 | 실제 상태 | `AGENTS.md` | 보안 문서 2종 |
|---|---|---|---|
| `large-directory-watch` path-count guard | 수정됨 (`e5c92c5`, 계획 18) | 있음 | 없음 |
| `split-view-async` fresh preview | 수정됨 (`e5c92c5`, 계획 18) | 있음 | 없음 |
| default-app-guide focus | 수정됨 (`47bef70`, 계획 19) | 있음 | "열림"으로 남아 있었음 — 낡음 |
| copy-button hover (= 이 계획서 A) | 수정됨 (이 작업) | **이미 있었음** (`792ece1`) | 있음 |
| ⌘B focus-guard (`toggleSidebarFromShortcut skips the toggle only while the source editor has focus`) | 수정됨 (`fcd7015`, 2026-09-16) | **없었음** | 있음 |

**계획서의 원래 표는 네 번째 행을 `AGENTS.md`에 "없음"으로 적었는데, 계획서를 쓴 직후 커밋
`792ece1`이 이미 추가한 뒤였다.** 계획서 자체가 자기가 경고한 실패 양식의 한 사례가 됐다.
실제로 `AGENTS.md`에 없던 것은 ⌘B 행 하나뿐이었다.

저장소 전체를 훑어 확인한 결과, 이 다섯 건의 상태 목록을 병행 관리하는 문서는 위 셋 외에 없다.
(`ci-electron.yml` 주석과 계획 18/19 문서는 서사이지 상태 목록이 아니다.)

## 설계 B — 실행한 것

1. **정본은 `AGENTS.md`.** ⌘B 행을 역사로 편입했고, 네 번째 항목을 "열림 + 포커스 가설"에서
   "수정됨 + 실측된 원인"으로 다시 썼다. 기각된 포커스 가설도 **기각됐다는 사실과 함께** 남겼다 —
   왜 이게 세 번의 수정 동안 안 보였는지가 그 기록의 값이다.
2. **`security-report.md`는 제자리 갱신.** 3건 나열을 걷어내고 게이트 신뢰 논지 + `AGENTS.md`
   참조로 바꿨다. 이 보고서가 단언했던 "OS 포커스 경합" 기전이 실측으로 기각됐다는 정정도 적었다.
   "Next Steps"의 안정화 항목은 남은 건수가 0이므로 제거하고 번호를 다시 매겼다.
3. **`memory-security.md`는 덮어쓰지 않고 추가.** PR #13이 확립한 방식 그대로 같은 항목 끝에
   `— **Corrected 2026-09-21:**` 를 덧붙였다. 2026-09-17의 문장은 한 글자도 지우지 않았다 —
   그날의 판단이 무엇이었는지가 그 파일의 존재 이유다.
4. **재발 방지 규칙 한 줄.** 플레이크 목록은 `AGENTS.md`에만 두고 다른 문서는 참조만 한다.
   두 곳에 같은 목록을 두면 반드시 갈라진다 — 이번이 가설이 아니라 증거다.

## 하지 않은 것

- **`--test-concurrency` 재조정.** 네 번째 오진이 됐을 것이다.
- **고정 지연이나 포커스 한 줄로 창 넓히기.** 계획 19가 같은 이유로 거부했다.
- **클립보드 스텁.** 계획서의 원안이었지만 프로브 2가 근거를 없앴다. 원인이 아니고, 실제 쓰기
  커버리지만 잃는다.
- **프로덕션 코드 수정.** 1.5초 뒤 버튼을 되돌리는 것은 올바른 UI다. 네 건 모두 앱이 아니라
  테스트의 결함이었다.
